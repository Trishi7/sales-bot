## 1. The intermittent T17 failure: cause, evidence, fix

**Cause: a harness problem. The product did the conservative thing in the bad run; nothing was ever applied that should not have been.**

- `verify_profile_lookup.py` named each bot's DB `f"b{id(model)}_test.db"`. Python reuses `id()` after garbage
  collection, so a later scenario sometimes reopened an EARLIER scenario's DB, with an open `row_add`
  (Janajit + Suryansh) still in it.
- Since the T21 fix, `propose_poc_add` leaves out anyone an open offer already names ("already asked"), so in that
  run no new proposal and no offer message were made. The scenario then replied "yes" to the last message in the
  channel log, which was the ANSWER. The vote path's `row_add` guard saw a reply to a message that is not the
  proposal's and correctly answered "not a vote" (the yes fell through to the engine: the 4th model call). The leftover
  proposal stayed open, nothing was appended. The other pass (fresh DB) offered, applied and appended. That is exactly
  the lead's symptom (open vs applied, 3 vs 4 calls, an append in one mode only).
- Evidence: before the fix, run 1 of 8 looped gave 3 FAILED, all `T17 duplicate` (proposals got
  `[('row_add','open','Add Suryansh Shukla to Outreach PoCs?',...)]`, want the two-person one). After the fix
  (a counter, `next(_DBN)`), zero T17 failures in 20+ looped runs. builder-1065 independently ran 120 live/test pairs
  over three hash seeds with 0 disagreements. `verify_replay_oct6.py` had the same `id(model)` line and the same
  intermittent `route: ['engine','engine']` failure; fixed the same way.
- No path was found where a "no", a non-approver or a non-reply applied anything (T14, T15, T16 hold).
- The offline guard recorded no violation during T17: the cause does not need a live read.

**The append can only hit the stub, never `gtm_sheet`'s real `append_row`.** `Sheet.install()` assigns
`gtm_sheet.SHEETS.append_row` on the singleton instance (shadowing the class method) in every scenario; the stub
only appends to a Python list; `SHEETS.tab` is stubbed to an in-memory tab; `write_cells`, `write_cells_on` and
`clear_cells` are replaced by recorders that raise. The real `append_row` is exercised only in
`tests/test_signed_row_append.py`, against a fake spreadsheet, with `SHEETS._open` replaced and the guard blocking the
real client.

**Live-source reads (item 13) were real.** `sources.status_report()` runs on every prompt build; with a service-account
key configured on this laptop its probes called `check_access()` / `read()` on the REAL Google sheet (read-only). Not
the cause of the flake, but my scripts were not offline. They now install the shared guard (below).

## 6. Cost at three levels (measured from the requests the engine really builds)

`verify_profile_lookup.py` COST: a model that keeps searching one at a time through 8 different queries (the worst
case), each search returning 8 results (80-character title, 250-character snippet). Request tokens = characters / 4
summed over every model call; Sonnet-class prices assumed ($3 in, $0.30 cache read, $3.75 cache write, $15 out per
million, ~150 output tokens a call). "Budget tokens" count cache reads at 10%.

| level | model calls | searches | request tokens | budget tokens | est. $ |
|---|---|---|---|---|---|
| old: 2 searches / 5 rounds (HEAD) | 6 | 2 | 84,209 | 35,546 | 0.128 |
| base: 4 searches / 7 rounds, no extension | 8 | 4 | 116,537 | 48,281 | 0.171 |
| extended: 6 searches / 9 rounds, extension fired | 9 | 6 | 133,281 | 54,837 | 0.193 |

Deltas for a question that keeps searching: old to base **+2 calls, +2 searches, +32.3k request tokens, +12.7k budget tokens,
+$0.043**; base to extended **+1 call, +2 searches, +16.7k request tokens, +6.6k budget tokens, +$0.022**; old to extended
+3 calls, +4 searches, +49.1k request tokens, +19.3k budget tokens, +$0.065 (the 7 Oct measurement for 6 / 9 was +$0.068 and
+20.3k, so the staged design adds nothing at the top and costs less for every question that stops at the base level). A question
that finishes in two or three searches costs the same at every level: the caps only bound the worst case.

Web pair on every question: two schemas plus the web rules block, about 1.5k tokens per call, all inside the cached prefix.
Search requests themselves are free (SearXNG / DuckDuckGo); each question banks up to 6 of `SEARCH_DAILY_BUDGET` (150 on
the real config).
